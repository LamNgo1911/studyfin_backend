Step 2 — Insert this new model block between `ProgramUniversity` and `enum Role`:

```prisma
// ─── Guidance Content ────────────────────────────────────────────────────────

model GuidanceSection {
  id         String   @id @default(cuid())
  programOid String
  program    Program  @relation(fields: [programOid], references: [oid], onDelete: Cascade)
  key        String
  title      String
  body       String
  order      Int
  createdAt  DateTime @default(now())
  updatedAt  DateTime @updatedAt

  @@unique([programOid, key])
  @@index([programOid])
}
```

Field rationale:
- `id` — cuid primary key (matches all other models in schema)
- `programOid` — FK to Program.oid (not Program.id) so guidance can reference the stable Opintopolku OID directly without a separate join
- `key` — slug-like section identifier (e.g. "application-process", "tuition-fees") — unique per program via @@unique([programOid, key])
- `title`, `body` — editorial content strings
- `order` — Int sort order for rendering A-Z section list
- `@@unique([programOid, key])` — prevents duplicate sections per program
- `@@index([programOid])` — fast lookup of all sections for a program

Do NOT use `@unique` on `programOid` alone — one program can have multiple guidance sections (multi-row per program).

GUID-01 specifies the model exists with programOid, sections, updatedAt, createdAt. The planning context refines sections into individual rows with key/title/body/order fields. Use the row-per-section design (not Json column) — it enables ordered reads without JSON parsing and supports future per-section updates.
