# Phase 01: Code Review Report

**Reviewed:** 2026-04-27T12:38:15Z
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

This phase introduces RBAC primitives (a `Roles` decorator, `RolesGuard`, `CurrentUser` decorator, and a `JwtStrategy` that now fetches role from the database), along with a Prisma schema that adds `User`/`Auth`/`Role` models, and two Prisma scripts (seed and cleanup). The NestJS guard and decorator implementations are clean and structurally correct. The primary concerns are: a hardcoded JWT fallback secret that makes the app silently insecure if the env var is missing, a guard that only checks method-level metadata (controller-level `@Roles()` is silently ignored), plaintext refresh token storage in the database, and sensitive tokens being logged to stdout in `auth.service.ts` (reviewed contextually, as it is a direct dependency of `jwt.strategy.ts`).

## Critical Issues

### CR-01: Hardcoded JWT Fallback Secret Allows Token Forgery

**File:** `src/modules/auth/strategies/jwt.strategy.ts:14`
**Issue:** When `JWT_SECRET` is not set in the environment, the strategy falls back to the string `'fallback-secret-change-in-production'`. This is a known, public value. Any attacker who knows it (it is committed to the repository) can mint valid JWTs for any user ID, bypassing all authentication. Because the fallback is silent (no warning, no crash), a misconfigured deployment will accept forged tokens indefinitely.
**Fix:**
```typescript
constructor(private readonly usersService: UsersService) {
  const secret = process.env.JWT_SECRET;
  if (!secret) {
    throw new Error('JWT_SECRET environment variable is not set. Refusing to start.');
  }
  super({
    jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
    ignoreExpiration: false,
    secretOrKey: secret,
  });
}
```

### CR-02: Plaintext Refresh Tokens Stored in Database

**File:** `prisma/schema.prisma:124`
**Issue:** The `Auth.refreshToken` column stores raw hex tokens generated by `crypto.randomBytes(32).toString('hex')`. If the database is compromised (SQL injection, backup exposure, insider access), every active user session can be immediately hijacked by replaying those tokens. Refresh tokens are long-lived credentials and must be treated like passwords.
**Fix:** Store a SHA-256 hash of the token in the database; compare using the hash at lookup time. The raw token is only ever held in memory and returned to the client once.

In `auth.service.ts` `issueTokens`:
```typescript
import { createHash } from 'crypto';

const refreshToken = this.generateToken();
const refreshTokenHash = createHash('sha256').update(refreshToken).digest('hex');

await this.prisma.auth.upsert({
  where: { userId: user.id },
  update: { refreshToken: refreshTokenHash, expiresAt },
  create: { userId: user.id, refreshToken: refreshTokenHash, expiresAt },
});

return { accessToken, refreshToken }; // raw token returned to client only
```

In `refreshTokens`, hash the incoming token before the lookup:
```typescript
const hash = createHash('sha256').update(refreshToken).digest('hex');
const auth = await this.prisma.auth.findFirst({ where: { refreshToken: hash }, include: { user: true } });
```

## Warnings

### WR-01: RolesGuard Silently Ignores Controller-Level @Roles() Decorator

**File:** `src/common/guards/roles.guard.ts:17`
**Issue:** `this.reflector.get(Roles, context.getHandler())` reads metadata only from the route handler method. If `@Roles('ADMIN')` is applied at the controller class level (a common pattern for protecting an entire controller), `requiredRoles` will be `undefined` and the guard will allow all requests — silently bypassing RBAC. `reflector.get` does not merge class and method metadata.
**Fix:** Use `reflector.getAllAndOverride` (method wins over class if both are set) or `reflector.getAllAndMerge` (union of both):
```typescript
const requiredRoles = this.reflector.getAllAndOverride<string[]>(Roles, [
  context.getHandler(),
  context.getClass(),
]);
```

### WR-02: Sensitive Tokens Logged to stdout

**File:** `src/modules/auth/auth.service.ts:62-64` and `149`
**Issue:** Email verification tokens and password reset tokens are written to `console.log` in plain text. In any deployment with centralised log aggregation (CloudWatch, Datadog, etc.), these one-time credentials will be persisted indefinitely and accessible to anyone with log access. This undermines the security of both flows.
**Fix:** Remove these `console.log` calls. Replace with a proper email-sending mechanism (even a no-op stub or a TODO comment without the token value). If logging is needed during development, gate it on `process.env.NODE_ENV !== 'production'` and never log the raw token value.

### WR-03: Missing Database Index on Token Lookup Columns

**File:** `prisma/schema.prisma:107-111`
**Issue:** `UsersService.findByEmailVerifyToken()` and `findByResetToken()` both call `prisma.user.findFirst({ where: { emailVerifyToken: token } })` and `findFirst({ where: { resetToken: token } })`. Neither `emailVerifyToken` nor `resetToken` has a `@@index` or `@unique` directive on the `User` model. Every call performs a full sequential scan of the `User` table.
**Fix:** Add indexes to the `User` model in `prisma/schema.prisma`:
```prisma
@@index([emailVerifyToken])
@@index([resetToken])
```
Alternatively, if token uniqueness can be guaranteed (tokens are 32 random bytes), declare them `@unique` to enable `findUnique` instead of `findFirst`, which is faster and more semantically correct.

### WR-04: Admin Seed Creates Account With Invalid Password Hash

**File:** `prisma/seed.ts:22`
**Issue:** When creating a new admin user, `passwordHash` is set to the literal string `'<hashed-placeholder>'`. This is not a valid bcrypt hash. The admin account will exist in the database with `ADMIN` role but cannot log in through the normal auth flow (bcrypt will always return `false` when comparing against a non-hash string). An operator seeding a production database may not notice this until they attempt to log in.
**Fix:** Require `ADMIN_PASSWORD` as a second environment variable and hash it before seeding, or document clearly that the password must be set separately:
```typescript
const adminPassword = process.env.ADMIN_PASSWORD;
if (!adminPassword) {
  console.error('ADMIN_PASSWORD environment variable is not set');
  process.exit(1);
}
const passwordHash = await bcrypt.hash(adminPassword, 10);

const user = await prisma.user.upsert({
  where: { email: adminEmail },
  update: { role: 'ADMIN' },
  create: {
    email: adminEmail,
    passwordHash,
    role: 'ADMIN',
  },
});
```

## Info

### IN-01: Roles Decorator Typed as string[] Instead of Role Enum

**File:** `src/common/decorators/roles.decorator.ts:3`
**Issue:** `Reflector.createDecorator<string[]>()` accepts any string, meaning `@Roles('admin')` (lowercase) or `@Roles('superuser')` will compile without error but will never match the `'ADMIN'` or `'USER'` values from the Prisma `Role` enum. A typo in any future `@Roles(...)` call will silently fail to protect a route.
**Fix:** Import and use the `Role` enum from Prisma:
```typescript
import { Role } from '../../../generated/prisma';
export const Roles = Reflector.createDecorator<Role[]>();
```
Update `RolesGuard` and `CurrentUserData.role` accordingly to use `Role` instead of `string`.

### IN-02: DATABASE_URL Used Without Null Guard in Prisma Scripts

**File:** `prisma/seed.ts:6` and `prisma/cleanup-non-english.ts:6`
**Issue:** `process.env.DATABASE_URL` is passed directly as `connectionString` to `PrismaPg`. If the variable is not set, `undefined` is silently passed and the error surfaces only when the first query runs, with a potentially confusing message. Both scripts already check `ADMIN_EMAIL` for an early exit; they should apply the same pattern to `DATABASE_URL`.
**Fix:**
```typescript
const connectionString = process.env.DATABASE_URL;
if (!connectionString) {
  console.error('DATABASE_URL environment variable is not set');
  process.exit(1);
}
const adapter = new PrismaPg({ connectionString });
```

### IN-03: RolesGuard Tests Do Not Cover Controller-Level Metadata

**File:** `src/common/guards/roles.guard.spec.ts`
**Issue:** All five test cases build an `ExecutionContext` mock with only `getHandler` defined. There is no test that applies `@Roles()` at the class level, which is consistent with the current implementation only checking `getHandler()` (see WR-01). Once WR-01 is fixed with `getAllAndOverride`, tests covering the controller-level case should be added to prevent regressions.
**Fix:** Add a test case that sets metadata on `getClass()` and verifies the guard enforces it:
```typescript
it('enforces @Roles() set at the controller class level', () => {
  reflector.get.mockImplementation((token, target) => {
    if (target === mockClass) return ['ADMIN'];
    return undefined;
  });
  // ...
});
```
